### B1 ★★☆☆☆ tiny-voca：4.5M 参数英文 TTS，训练数据全是 Qwen3-TTS 合成语音，CPU 实时 70 倍（11-16）

〔B·开源模型〕

![图源：github.com 原文配图](https://opengraph.githubassets.com/ca8f77cf5bec926dafe81e8597aad7cc432cafc378e19f2e880ccd0651e12667/n4ze3m/tiny-voca)

## Agent 工程

### D1 ★★★★☆ 腾讯技术工程：对照 DeepSeek Super-Agent，拆解开源 Octop 的团队模式（Router + 专家 Agent）（11-16）

〔D·Agent 工程〕

![图源：mp.weixin.qq.com 原文配图](https://mmbiz.qpic.cn/sz_mmbiz_jpg/KVER9adz905ZZJtKBJTHm5xluEY8XRmX8U9FzRvXrtZqWeSjJ1apETvfic3v64XoSuQe0bDpOYCIsggpgbiarn6a00uGcMfq7iaeTIFMicuLSL8/0?wx_fmt=jpeg)

*Octop 团队（腾讯云） · 公众号 腾讯技术工程 · 11-16*

Octop 负责人对照 DeepSeek 的 Super-Agent 设计（前端 Router 接请求并分派、后端多个 Worker 并行、长任务转后台、消息只留核心上下文、材料按需检索），介绍腾讯云开源的 Octop 1.0.2「团队模式」：主持人拆解任务分派，多名专家 Agent 并行执行，目标是连续性、高效率、主动性和持久性。 [\[24\]](https://mp.weixin.qq.com/s/5r_EhRzdgRgzg8kWmZDyRQ)[\[25\]](https://github.com/TencentCloud/Octop)

- 调度员和执行单元分开，不在一个会话里串行做完
- 长任务后台化，前台继续接新请求
- 上下文只留核心，材料按需取
- 主动性要能判断该不该介入

### D2 ★★★★☆ 京东技术：11.11 大促保障里的 Super Agent「数字人队长」——进群、跨群记忆、主动干活（11-16）

〔D·Agent 工程〕

![图源：mp.weixin.qq.com 原文配图](https://mmbiz.qpic.cn/sz_mmbiz_jpg/BdwSyGJqvPpp78ial9L1qSCq3v83liaxg6fbfWhyA0kiaRzG122FpDTibtj4gb9Wshbj2ibic3XiagnDOQpeFgT3cUKt9DMK63GEsEiaiavMQYHbsnj8/0?wx_fmt=jpeg)

*京东技术 · 公众号 京东技术 · 11-16*

京东介绍 11.11 保障中的「数字人队长」：进驻京 Me 工作群的 Super Agent，共享群上下文、跨群记忆，能主动发言并调用工具做架构评审、容量风险评估和代码风险分析。保障期间以小队形式出现，分别承担备战统筹、高可用架构、GOC、SRE 和技术支持；人负责关键判断和责任，数字人负责在线、聚合、分析和协同。 [\[26\]](https://mp.weixin.qq.com/s/QbU-Q1-qnV6GwlYwOrdpPQ)

- 把 Agent 放进已有协作现场，而不是另开控制台
- 跨会话、跨群记忆
- 主动介入，但关键决策由人承担
- 把专家经验沉淀成可调用能力

## 搜索、排序与推荐

### E1 ★★★★☆ RecMem：循环记忆压缩把长交互历史压进固定槽位，16 个 slot + 216 token 对标 HSTU-1200（11-16）

〔E·搜索、排序与推荐〕

*🏛 （单位见原文） · Haoyi Hu, Gaoyang Guo, Yunjia Xi 等 · arXiv 2611.17921 · 11-16*

生成式推荐受益于更长的交互历史，但直接处理的计算成本随长度增长，截断又丢信息。 [\[33\]](https://arxiv.org/abs/2611.17921)

- **方法**：把历史片段循环压缩进固定数量的 memory slot，下层共享的编解码器加槽级遗忘门，用推荐损失训练记忆。
- **结果**：在 MerRec 上用 16 个 memory slot、216 token 解码上下文，对比 HSTU-1200 的 1,200 token；其余指标见原文实验表。

### E2 ★★★☆☆ RACE：按排序不确定性自适应分配容量，做高效序列推荐定制（11-16）

〔E·搜索、排序与推荐〕

![图源：arxiv.org 论文首图](https://arxiv.org/html/2611.18244v1/race_intro_0523.png)

*🏛 （单位见原文） · Tianqi Liu, Kaipu Sun, Kairui Fu 等 · arXiv 2611.18244 · 11-16*

序列推荐定制时，所有请求用同样的计算容量，确定的请求浪费、不确定的请求不够。 [\[34\]](https://arxiv.org/abs/2611.18244)

- **方法**：用排序不确定性调节定制容量，不确定就加计算、确定就走轻量。
- **结果**：具体数字见原文实验。
